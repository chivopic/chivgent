# 从 issue 到可审查的 PR

[English](issue-workflow.md)

本页是处理一个 issue 的执行顺序。验收标准在 [代码规范](code-standards.md)：一次改动要包含什么、测试要证明什么、评审怎么做。开工前要先看 [contributors](contributors.md) 里的 harm check，以及 [LESSONS.md](../LESSONS.md) 里已经犯过的错。本页不新增规则，只把现有规则按使用顺序排好。

一个 issue 是对可观察行为的报告，不是“照这个补丁改”的命令。

## 每个 issue 必须有结局

不允许 issue 停在“看过了”。每个 issue 最终落到下面四种结局之一，并留下证据：

| 结局 | 什么时候用 | 留下什么 |
| --- | --- | --- |
| 修复 / 实现 | 行为明确，测试能锁住，改动在允许范围内 | 一个 PR，写 `Closes #N`；提交和 PR 里都有验证记录 |
| 拆分 | 一个 issue 里有多个独立行为，或依赖另一个未完成项 | 原 issue 保留；列出子 issue 的范围、顺序和依赖 |
| 不做 | 由维护者决定，例如会改变只读默认、沙箱或权限模式 | 维护者给出理由；代理只整理证据，不关闭 issue |
| 阻塞 | 缺凭据、缺平台、缺产品决定，或无法写出可观察行为 | 写明缺什么、谁能解除、解除后第一步做什么 |

“阻塞”是结论，不是通过。代理不关闭、不批准、不合并；它把证据写好，由维护者决定。

## 1. 把报告还原成可观察行为

动手前先写四行：

- **触发**：哪条命令、哪个按键、哪个 flag 或哪种状态。
- **现状**：今天实际发生什么，带上准确输出或退出码。
- **期望**：issue 要求发生什么。
- **观察点**：哪个测试能看出两者的差别。

例子（#91）：触发是 `/login` 不带参数；现状是直接出现 `API key for openai`；期望是先出现 Provider 选择器；观察点是测试里先看到 `Select a Provider for /login`，选择后才看到 `API key for deepseek`。

四行写不出来就停下来问。只描述“把函数挪个位置”的 issue 是建议，不是需求；真正的 bug 可能在别处。

然后到 [代码规范的文档表](code-standards.md#documented-behavior) 找到拥有这段行为的页面，读页面并核对它链接的源码。`docs/stage-*.md` 和 `docs/tui-v*.md` 是历史记录，不是契约。

## 2. 判断改动是否允许

以下决定属于维护者，issue 要求改动时必须停：

- 默认只读；
- 沙箱不可用时的 fail-closed；
- 权限模式只在当前进程有效；
- shell 清理与 `--serve` 关闭是两条不同的路径。

[contributors 的 harm list](contributors.md#look-for-harm-first) 里的任何一项也一样：改 `.github/`、新增网络地址或上传、读写真实凭据、新增依赖或安装脚本、削弱沙箱。

这类 issue 仍然可以分析、写方案、估风险，但实现由维护者决定。不要用“为了完成任务”作为绕过权限或凭据边界的理由。

## 3. 按 issue 类型选择路径

类型决定先看什么、必须产出什么、最容易错在哪：

| 类型 | 先看 | 必须产出 | 常见坑 |
| --- | --- | --- | --- |
| 行为缺陷 | 最小复现、拥有该行为的契约页、同一谓词的所有调用方 | 一个删除修复就会失败的回归测试 | 只修一条分支；只测函数不测整条路径 |
| 新功能 / 新命令 | 现有命令的注册、帮助文本、参数解析和文档入口 | 用户可见行为的测试、`/help` 更新、README 或契约页 | 命令能跑但没有文档；参数校验只覆盖正常值 |
| TUI / 交互 | 输入解析、重绘、终端宽度和高度、无 TTY 的回退 | 读写终端字节或终端模拟器的测试；界面截图或录屏 | 只在宽终端正确；没有覆盖窄屏、Unicode、分片转义 |
| 安全 / 权限 / 沙箱 | `docs/shell-sandbox.md`、`src/permissions.ts`、拒绝路径 | 失败关闭的测试；拒绝时的准确报错 | 增加无沙箱回退；把拒绝当成“空结果” |
| Provider / OAuth / 凭据 | `docs/subscription-oauth.md`、provider 注册表、凭据读写 | 离线 fake 的协议测试；真实配置一份都不碰 | 把订阅凭据当 API Key；写错 auth 文件权限 |
| 会话 / 恢复 | 会话存储格式、迁移、权限模式不随会话恢复 | 旧会话可读的兼容测试；恢复后的行为测试 | 恢复权限模式；把缺失字段当成空值 |
| 扩展 / 远程 | `docs/extensions-and-remote.md`、协议事件 | 协议级测试；断连和取消路径 | 信任远端内容为指令；权限被扩展继承 |
| 桌面端 | `docs/desktop-architecture.md`、`apps/desktop` | `npm run desktop:test`、`npm run desktop:build` | 只跑根目录 `npm test`（它不含 desktop） |
| 文档 | 契约页、链接目标、实际源码 | 链接可解析；改动与源码一致 | 改 `stage-*` / `tui-v*` 历史；复制第二份事实 |
| 性能 / 重构 | 基线数据、调用方、可观察行为是否改变 | 行为不变的测试；前后对比数据 | 借重构顺手改行为；没有基线就宣布更快 |
| 发布 | `docs/releasing.md`、`npm run release:check` | 版本、changelog、打包检查 | 在脏工作区发布；跳过 dry run |

一个 issue 同时属于多类时，按最危险的那类走，并在 PR 里说明其余部分没有改。

## 4. 限定范围

一个 issue、一个分支、一个 PR。拆开：

- 行为修复和无关重构；
- 两个只是改了同一个文件的 issue；
- 行为变更和新功能。

动手前写清楚：

- 从用户输入到最终结果的运行时路径，包括消费它的调用方；
- 共享同一判断的兄弟路径：CLI、TUI、远程 REPL、桌面宿主；
- 需要更新的契约页；
- 放失败测试的文件。

超过一个文件的改动先写计划。计划里要写“哪些保持不变”，不能只写“改什么”。

## 5. 复现并锁住行为

在最新 `main` 上复现，保存命令和输出。先写测试，再改代码；把测试跑在旧代码上，确认它因为 issue 描述的行为而失败。缺 import、测试被跳过、fixture 为空都不算失败。

测试要求：

- 不访问网络；
- 不读写 `~/.chivgent`、真实 provider key、运行中会话的 socket；
- 测试启动的东西在测试结束前停掉；
- 断言用户或调用方需要的行为，不绑定内部实现；
- 时间相关的测试两边留余量，靠注入延迟复现，不靠多跑几次。

例子：处理 #90 时，把记录区 wheel-up 的测试跑在旧 `editor-input.ts` 上，它期望 mouse-off 序列，实际收到一次重绘和 DSR 查询；恢复修复后通过。多行草稿的滚轮测试在旧代码上本来就通过，它只是回归保护，不能算作“删除修复会失败”的证据。

## 6. 实现

按 [代码规范](code-standards.md#what-a-change-contains) 写。特别检查：

- 改 flag、退出码、权限模式或异步时序时，重新找出所有调用方、保存的副本和假设了旧含义的测试。
- 失败读取、解析或哈希都表示“未知”，不表示空、没有或相等。
- 默认值不能覆盖用户显式设置的值。
- 改文档拥有的行为时，同一个 PR 更新拥有它的页面；一个事实只留一处，其余地方链接过去。
- 不碰 `docs/stage-*.md`、`docs/tui-v*.md`。
- 不夹带附近的重构或格式化。

## 7. 验证并记录证据

按改动涉及的面选择检查：

| 涉及面 | 检查 |
| --- | --- |
| 任何改动 | `npm run check`、`npm test`、`npm run build` |
| CLI、Provider、权限、eval | `npm run eval -- --dry-run --allow-writes --allow-shell` |
| shell 沙箱、打包 | Node.js 22 上 `node scripts/docker-smoke.mjs`；`npm pack --dry-run` |
| `apps/desktop` | `npm run desktop:test`、`npm run desktop:build` |
| 发布候选 | `npm run release:check` |

`npm test` 不包含 `apps/desktop`；改了桌面端不能只跑根目录测试。

还要做 CI 做不了的那一步：把旧源码放回去，只跑新增测试，确认它按预期失败，再恢复修复并确认通过。新文件要先移走，否则恢复后仍是新代码。一次可行的手工流程：

```sh
git diff -- src > /tmp/change.diff
mv src/path/to/new-file.ts /tmp/new-file.ts   # 若本次新增了文件
git checkout -- src
npx vitest run tests/the-new-test.test.ts     # 必须因行为失败
git apply /tmp/change.diff
mv /tmp/new-file.ts src/path/to/new-file.ts
npx vitest run tests/the-new-test.test.ts     # 必须通过
```

记录：

- 失败的测试名和真实失败信息；
- 恢复后通过的测试名；
- 实际跑过的命令和结果；
- 跑不动的平台、终端或账号，写成“没跑”；
- 需要时写清 Node 版本（CI 是 22 和 24）。

真实终端、真实平台或真实账号能验证的，就验证。没试过的不能写成可用。

同一份证据写进提交说明和 PR 的 Testing，聊天记录不算。

## 8. 提交并打开 PR

先从最新 `main` 切分支，分支只服务这个 issue。

提交说明：

- 标题写区域和用户可见的行为；
- 正文写第 7 步的验证、删除修复后失败的测试名、以及没跑的项目；
- 不把提交列表复述一遍。

PR 使用 [仓库模板](../.github/pull_request_template.md)：

- `What?`：用户现在看到什么不同；
- `Why?`：问题是什么，为什么现在做；
- `How?`：实现和取舍；
- `Testing`：跑过什么、没跑什么、删掉修复后哪个测试会失败；
- `Risks`：兼容、权限、退出码、性能；
- `Screenshot`：界面改动必须给截图或录屏；环境无法录制时说明原因，并展示真实渲染的帧，不能把 mock-up 说成终端截图。

只有这个 PR 真正完成 issue 时才写 `Closes #N`；只完成一部分写 `Refs #N`，并按第 3 步的“拆分”留下后续 issue。链接契约页、实现和验证。

不要在一个分支里夹带第二个 issue，也不要提交另一个会话的 worktree。

## 9. 评审后停步

维护者拉取 head，合到当前 `main`，在合并结果上跑验收检查。评审会故意删掉修复，确认新测试能抓住。评审后的任何推送都触发重新评审。

代理可以回答问题、补证据、改代码，但不批准、不自行请求变更、不关闭 issue、不合并。合并由维护者执行。

同一个问题在评审里再次出现时，把日期、证据和能提前抓住它的规则写进 [LESSONS.md](../LESSONS.md)。同一课在三个不同日期出现后，移进代码规范。

## 必须停下来的情况

出现以下任一情况就停，并把原因写在 issue 或 PR 里：

- 写不出四行可观察行为；
- 改动需要维护者决定的事项，或 harm list 里的任一项；
- 没有任何测试能在删除修复后失败；
- 要落地必须夹带无关重构；
- 找不到拥有该行为的契约页和对应源码；
- 验证需要真实机器、真实凭据，或 issue 没有覆盖的网络请求。

“阻塞”是一个需要处理的结论，不是一个通过。

## 证据模板

复制到提交说明或 PR 的 Testing 里，按实际情况增删：

```text
删除修复后失败：<测试名> — <真实失败信息>
恢复后通过：<测试名>
已跑：npm run check；npm test（N 通过，M 跳过）；npm run build；<其余按面>
没跑：<桌面端 / Docker smoke / eval / 真实终端 / 真实账号，以及原因>
契约页：docs/<page>.md
手动验证：<平台、命令、结果；没做就写没做>
```
