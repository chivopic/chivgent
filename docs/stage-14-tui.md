# Stage 14: TUI —— 事件流到视图层的那道边界

> 目标版本：`0.17.0`
> 状态：已实现（2026-09-08）。本文先于实现写成，实现中发现的问题记在第 8.1 节。

> Stage 3 造了 `AgentEvent` 流，此后每一阶段都往它上面挂东西：流式输出、会话日志、
> 扩展、远程客户端。但这些消费者有一个共同点——**它们都是追加式的**。事件来了就打印，
> 打印完就忘掉，屏幕上的内容从不回头修改。
>
> TUI 是第一个**反向**的消费者：它要从这条流里**重建出"现在是什么状态"**，然后把那个
> 状态画出来，并在下一个事件到达时更新它。这件事能不能做干净，是对前面十三个阶段划的
> 边界的一次检验。Stage 14 只回答这个问题。

## 1. 目标

```text
AgentEvent 流
  -> reduce(state, event) -> ViewState     纯函数，不碰终端
  -> view(state, width)   -> string[]      纯函数，不碰终端
  -> paint(previous, next)                 唯一碰终端的地方
```

完成后：

1. 跑起来的时候，屏幕底部有一块**活的区域**：现在是第几轮、在想还是在跑工具、
   哪几个工具在跑、各自的最新输出、已经花了多少 token、跑了多久。
2. 这块区域随事件更新，**不重画整屏**，也不破坏上面的滚动历史。
3. `reduce` 和 `view` 有完整的单元测试，**一行终端代码都不需要**。

第 3 条是本阶段的重点。前两条是它的证据。

## 2. 为什么不照抄 pi 的渲染器

pi 的 TUI 大约 18000 行，主体是一个单元格级的差分渲染器。chivgent 整个项目
11000 行。照抄它，学到的主要是"怎么写终端渲染器"——那是个通用图形问题，和 Agent
架构没有关系。

**值得学的那个问题是：一条为"追加"设计的事件流，能不能撑起一个需要"重建"的消费者。**
这个问题的答案在 `reduce` 里，不在画布里。所以本阶段把渲染压到能证明 reduce 是对的
那个最小程度，把省下来的注意力全部放在状态模型上。

判断标准也跟着定下来：**如果一个决定不影响"事件流能不能重建状态"，它就不属于本阶段。**
下面三个决定都是这么来的。

### 2.1 不接管备用屏（alternate buffer）

全屏 TUI 要 `smcup` 切到备用屏，代价是**滚动历史没了**——翻不回上一个回答，
某些终端里跨边界的选中复制也会坏。要补回来就得自己实现滚动缓冲、搜索、选中，
那又是几千行，而且和 Agent 架构无关。

做法：**已完成的内容照旧打进正常的滚动历史**（追加式，和今天一样），TUI 只拥有
**底部那一小块活的区域**。turn 结束时把这一轮刷进历史、从状态里丢掉。

这个决定还带来一个好性质：**状态是有界的**。全屏 TUI 必须把整个会话留在内存里以便重画，
而这里只需要留住"正在发生的事"。

### 2.2 不自己写行编辑器，输入继续交给 readline

一个 TUI 通常要接管输入：raw 模式、自己处理退格、左右键、历史、Home/End。那大概
150 行，而且**它不教任何关于 Agent 架构的东西**。

做法：**readline 继续拥有最后那一行**，活的区域画在它上面，画完把光标还回去。
`/login` 那个关掉回显的技巧（0.14.0 踩过 `readline.question()` 和循环的迭代器抢输入
的坑）也就原样能用。

代价是活的区域只能在提示行上方，不能覆盖全屏。对本阶段要回答的问题没有影响。

### 2.3 行级差分，不做单元格级

`paint` 比较上一次和这一次的行数组，**只重写内容变了的行**。约 150 行。

理由：这里的代价模型是"往终端写了多少字节"。行级粒度已经把最常见的情况——状态行上的
计时器在跳——从"重画整块"降到"重写一行"。单元格级能省的那部分，在一个只有五六行的
区域里不值得。

## 3. ViewState 的形状

```ts
export interface ViewState {
  /** 没有运行时是 undefined。活的区域这时只有输入提示。 */
  readonly run?: RunState;
}

export interface RunState {
  readonly turn: number;
  readonly maxTurns: number;
  readonly startedAt: number;
  /** 本轮已经流出来的助手文本。turn_end 时刷进历史并清空。 */
  readonly text: string;
  /** 正在跑的工具，按启动顺序。结束的从这里移走。 */
  readonly running: readonly RunningTool[];
  readonly usage?: UsageTotal;
  readonly status: "thinking" | "running-tools" | "done";
}

export interface RunningTool {
  readonly toolCallId: string;
  readonly name: string;
  readonly target?: string;
  /** 该工具最近一次 tool_execution_update 的快照。 */
  readonly progress: string;
  readonly startedAt: number;
}
```

`target` 复用 Stage 13 给 eval 报告写的那个提取逻辑（`path` 参数，或截断的 `command`），
两边共用一份。

## 4. 一个必须处理对的不对称：delta 与 snapshot

`message_update` 带的是**增量**（`delta`），`tool_execution_update` 带的是**快照**
（`content`，已经被截断到一个有界窗口）。

今天的渲染器**不需要知道这个区别**——它只管把收到的东西打出去，两种都直接写就对了。
一个有状态的视图必须知道：

- 对 delta 用替换 → 只剩最后一个 token，整个回答丢了。
- 对 snapshot 用追加 → 同一段输出被重复堆积，而且因为快照是截断过的，
  拼出来的东西根本不对。

```text
message_update        state.text += event.delta
tool_execution_update tool.progress = event.content
```

这是本阶段唯一一处"事件流的设计选择直接决定了消费者必须怎么写"的地方，
所以 `reduce` 的测试要**专门覆盖它的两个反面**：对 delta 做替换会丢内容，
对 snapshot 做追加会重复。这两条测试是本阶段的核心资产。

（顺带说明：事件本身的设计是对的。`message_update` 用 delta 是为了让流的长度线性于
回答长度；`tool_execution_update` 用 snapshot 是因为一个被丢过头部的 delta 流
重组不出正确的窗口。见 `src/events.ts` 上的注释。）

## 5. 什么时候用它

- `--tui` 开关，**只在交互模式下有意义**：一次性问答没有"活着"的东西要维持。
- 需要 `stdin` 和 `stderr` 都是 TTY。不满足时**明确报错，不静默退回**——
  静默退回会把一个用错的命令伪装成正常行为。
- 活的区域写 **stderr**，和今天的工具活动一致。stdout 仍然只有回答，保持可管道。
- **本阶段不设为默认。** 先让它跑一段时间，证明在真终端里不会把屏幕搞乱，再谈默认。

## 6. Ctrl+C 与改变窗口大小

两件必须现在就想清楚的事，因为它们决定 `paint` 的接口：

- **Ctrl+C**：今天的语义是"取消正在进行的回答，不杀进程"。TUI 要在取消后把活的区域
  收干净（刷掉、把光标还给 readline），否则残留的行会留在屏幕上。
- **改变窗口大小**：宽度变了，上一次画的行数组就不再对应屏幕上的内容，
  **行级差分的前提失效**。做法是 `SIGWINCH` 时丢弃差分基准，整块重画一次。
  这是唯一允许整块重画的时机。

## 7. 测试策略

单元测试（不需要终端，进 `npm test`）：

- `reduce`：喂一串真实形状的事件，断言状态。**必须包含第 4 节那两条反面测试。**
- `reduce`：`turn_end` 之后本轮文本被清空、结束的工具从 `running` 里移走。
- `reduce`：两个工具并发运行时，各自的 progress 不互相覆盖（今天的 `\r` 进度行做不到
  这件事，这是 TUI 带来的实际改善之一）。
- `view`：窄终端下的截断；没有运行时只有提示行；工具多到放不下时的省略。
- `paint`：只重写变了的行——用一个假的 `OutputStream` 记录写了什么，
  断言没变的行**一个字节都没写**。这条是行级差分唯一的验收方式。
- `paint`：宽度变化后整块重画。

端到端：用 stub Provider 在一个假 TTY 上跑一轮，确认活的区域出现、更新、
在 turn 结束时刷进历史、退出时收干净。

## 8.1 实现中发现的问题

**`stream.columns` 可能是 `0`，而不只是 `undefined`。** 我写的是
`stream.columns ?? 80`——`??` 只挡 `undefined` 和 `null`，`0` 会原样穿过去。
在一个没设过大小的 pty 里（`script(1)` 起的就是），宽度于是变成 0，`fit()` 退到
`MINIMUM_WIDTH`，**每一行都被砍到 20 个字符**：状态行成了 `thinking · turn 0…`。

单元测试抓不到它——测试里我传的是 `width: () => 80`。是端到端在真 pty 上跑才露出来的。
这是本阶段的第二次"单测全绿但真跑不对"，和 Stage 12 那次（`buildContext` 每轮都加
`context.usage`，没压缩时是 `undefined`，于是每一次真实运行都被标成不完整）同一类。
判据改成"必须是正数才有意义"，并补了测试。

**`onBeforePaint` 钩子设计了但没用上。** 我原本以为画之前需要让调用方把光标停到别处。
实际上 `Painter` 自己的不变式——**光标永远停在区域下方那一行空行上**——已经把调用方的
提示行让出来了，不需要额外协调。删掉了，没留在代码里。一个"以防万一"的钩子和一条
永远不会失败的判定是同一种东西。

**已知限制：运行中打字会打乱区域。** readline 仍然拥有输入行并且会回显每一次按键，
而运行期间 REPL 并不读取输入。所以运行中敲键盘，回显会落进区域，破坏"光标停在区域
下方"这个不变式。修法是运行期间 `readline.pause()`，但那会牵动 Ctrl+C 的送达路径，
而 Ctrl+C 取消是比这个更重要的行为。**本阶段不修，记在这里**——`--tui` 是非默认开关，
这个取舍是明确的，不是疏忽。

## 9. 不在本阶段

- **备用屏、滚动缓冲、搜索、鼠标、选中复制。** 见 2.1。
- **自己的行编辑器、键位注册表。** 见 2.2。输入归 readline。
- **扩展注册 UI 组件**（Stage 9 砍掉的那一半）。它要的是键位与覆盖层，
  而这两样都建立在接管输入和全屏之上——那是下一阶段的事，不是这一阶段。
- **单元格级差分、语法高亮、Markdown 渲染。** 见 2.3。
- **远程客户端接 TUI。** Stage 10 的客户端也是一个事件流消费者，接上去是自然的，
  但它会引入"事件迟到 / 乱序"这一类本地跑不会有的问题。等本地这条路稳了再说。
- **把 `--tui` 设为默认。** 见第 5 节。
