# Stage 10: 远程会话

> 目标版本：`0.12.0`
> 状态：**设计中，尚未实现**（与 Stage 8、9 一样先于实现写成）

> 到 Stage 9 为止，chivgent 的会话和跑它的那个终端是绑死的：进程在哪，会话就在哪，
> 关掉终端会话就断了，另一个窗口也看不到它。Stage 10 解决"会话可以被别的进程接上"
> 这一件事——一个 chivgent 进程持有 Session，其他进程通过一个本地 socket 连上去发
> prompt、看事件流。不引入 TUI、不引入网络监听、不引入多会话路由。

## 1. 目标

```text
chivgent --serve                       持有 Session 的服务端
  <CHIVGENT_HOME>/sockets/<id>.sock
        ^                    ^
        |                    |
  chivgent --connect <id>    chivgent --connect <id>
   发 prompt / 收事件          只看事件（观察者）
```

完成后：

1. `chivgent --serve` 把一个会话暴露在本地 socket 上并常驻。
2. `chivgent --connect <id>` 从另一个终端接上去，像在本地一样提问。
3. 第二个客户端可以同时接上**观察**同一个会话的事件流。
4. 客户端断开不影响正在跑的运行；重新连上能继续。

## 2. 为什么这一步是架构问题

Stage 3 把运行过程拆成了一串 `AgentEvent`，Stage 4 让 Session 成为事件的唯一分发点
并支持多订阅者。当时这两件事看起来只是为了让渲染器和会话日志各自消费同一个流。

远程会话是这两个设计的兑现：**一个客户端不过是又一个订阅者，只是它在另一个进程里。**
如果事件模型当初设计成"渲染器专用"，这一阶段就得先推倒重来。现在不用——服务端要做的
只是把已有的事件 JSON 化后写进 socket，而 `--json` 模式早就证明了这些事件可以逐行
序列化。

这也是为什么本阶段**不做** TUI：TUI 是绘制问题，而这一步能检验前面的边界划得对不对。

## 3. 设计原则

1. **服务端持有 Session，客户端不持有状态。** 客户端只是发 prompt、收事件、画出来。
2. **事件流是单向广播。** 所有连上来的客户端看到同一份事件，先后到达顺序一致。
3. **一次只跑一个 prompt。** 与 REPL 同一条规则：并发运行会共享同一份 transcript。
4. **客户端的生死不影响运行。** 断开只是少了一个订阅者，不取消正在跑的运行。
5. **协议是 JSON Lines。** 与会话日志、`--json` 同一种形状。
6. **socket 的能力等于服务端启动时的能力。** 这一点必须写进文档而不是靠猜。

## 4. 传输与分帧

Unix domain socket，`node:net`，零依赖。路径：

```text
<CHIVGENT_HOME>/sockets/<session id>.sock
```

**分帧用 JSON Lines**，一行一个 JSON 对象，`\n` 结束。

pi 用的是 4 字节大端长度前缀 + CBOR。它需要那个是因为要传图片和附件；chivgent 的
消息全部是 JSON 可序列化的——这是 `AgentEvent` 从 Stage 3 起就有的不变量
（"Every event is a plain, structured-cloneable object"）。JSONL 因此够用，而且零依赖、
可以直接用 `nc` 看。代价写清楚：**如果以后要传二进制附件，这一层要换成长度前缀**。

行长度设上限（1 MiB）。超长的行会被当作协议错误关闭连接，而不是无限缓冲——一个不说
人话的对端不应该能把服务端的内存吃光。

## 5. 协议

版本号一个整数，握手不匹配直接拒绝并说明双方版本。省下的是几年后"为什么行为很怪"
的排查时间。

### 客户端 -> 服务端

| type | 字段 | 含义 |
| --- | --- | --- |
| `hello` | `version` | 必须是第一条 |
| `prompt` | `text` | 发起一次运行 |
| `interrupt` | — | 中断正在跑的运行（等价于 Ctrl+C） |

### 服务端 -> 客户端

| type | 字段 | 含义 |
| --- | --- | --- |
| `hello` | `version`, `session`, `tools` | 握手成功，附会话头和工具名 |
| `error` | `code`, `message` | 协议或运行错误；`code` 用于程序判断 |
| `event` | `event` | 一条 `AgentEvent`，原样透传 |
| `bye` | `reason` | 服务端要关掉这条连接 |

事件套一层 `{"type":"event","event":{...}}` 而不是裸发 `AgentEvent`，这样协议自己的
消息和 agent 的事件永远不会混淆——否则将来 agent 加一个叫 `error` 的事件类型就会撞车。

错误码（首批）：`version_mismatch`、`busy`、`bad_message`、`too_large`、`agent_error`。

## 6. 并发与观察者

- 一个 prompt 在跑时，另一条连接发来的 `prompt` 返回 `busy` 错误，**不排队**。
  排队意味着服务端要替用户决定"你的问题在别人后面"，而客户端此时完全可以自己重试。
- `interrupt` 任何连接都能发。中断的是会话，不是"你的"运行——这跟本地 Ctrl+C 一致。
- 新连上的客户端拿到 `hello`（含会话头），**不重放历史事件**。要看历史，会话日志在那里；
  在 socket 上重放会让"事件流"同时意味着两件事。

## 7. 生命周期

- **启动**：先 `mkdir` 父目录且 `mode 0o700`，再 bind，bind 成功后把 socket `chmod 0o600`。
- **陈旧 socket**：路径已存在时先尝试连接。连得上说明有活的服务端，拒绝启动并报出
  路径；连不上（`ECONNREFUSED`）说明是上次崩溃留下的，删掉再 bind。
- **退出**：`SIGINT`/`SIGTERM`/正常退出都要 unlink socket 文件。
- **客户端**：服务端消失时报明确的错误，而不是挂住。

## 8. 安全模型

**连上这个 socket 的人，拥有服务端启动时的全部能力。** 如果服务端是
`chivgent --serve --allow-shell` 起来的，那么任何能连上的进程都能让模型执行命令。

因此边界是文件系统权限，而且**真正起作用的是目录权限**：`node:net` 不能在 bind 时指定
mode，socket 文件在被 `chmod` 之前有一个短暂的窗口。把父目录设成 `0o700` 就关掉了这个
窗口——别人根本进不到那个目录里去。socket 本身仍然 `chmod 0o600` 作为纵深防御。

pi 的做法是先 bind 到一个临时路径、再 hardlink 到正式路径、然后 chmod，用来消除那个
窗口。在目录已经是 `0o700` 的前提下这一步是多余的，所以不抄。

不监听 TCP。跨机器访问请用 SSH 端口转发——那样认证和加密由 SSH 负责，而不是由这个
200 行的协议负责。

## 9. CLI

| 调用 | 行为 |
| --- | --- |
| `chivgent --serve` | 起一个会话服务端，打印 socket 路径，常驻 |
| `chivgent --serve --resume ID` | 同上，但恢复已有会话 |
| `chivgent --connect ID` | 连上并进入交互模式 |
| `chivgent --connect ID "问题"` | 连上、问一次、退出 |
| `chivgent --connect PATH` | 直接给 socket 路径 |
| `chivgent --servers` | 列出还活着的服务端 |

`--serve` 与所有能力开关组合有效（`--allow-writes`、`--allow-shell`、扩展），并且在
启动横幅里**明确打印这次授予了哪些能力**——因为连上来的人看不到你敲了什么。

## 10. 对既有模块的影响

- 新增 `src/remote/`：协议、分帧、服务端、客户端、socket 路径与发现。
- `cli.ts`：三个新入口。
- `repl.ts`：交互循环目前直接调 `session.prompt()`。远程客户端需要同样的循环但走
  socket，因此把"读一行、判断斜杠命令、跑一次、渲染"抽象成一个可以由本地 Session 或
  远程连接实现的小接口。
- **Agent、Workspace、Provider、Context、Extensions 全部不受影响。**

## 11. 测试策略

1. 分帧：拆包/粘包/空行/超长行。
2. 协议校验：非法 JSON、缺字段、未知 type、握手前发 prompt。
3. 版本不匹配：双方都收到可读的错误。
4. 往返：`prompt` 产生的事件按顺序到达客户端，`agent_end` 收尾。
5. 观察者：两个客户端收到同一串事件。
6. `busy`：运行中第二个 prompt 被拒绝，且第一个运行不受影响。
7. `interrupt`：另一条连接发来的中断能停掉运行。
8. 断开：客户端中途断开，运行照常完成，服务端不崩。
9. 陈旧 socket：留一个死掉的 socket 文件，服务端能接管；留一个活的，服务端拒绝启动。
10. 权限：socket 父目录 `0o700`，socket 文件 `0o600`。
11. 退出清理：服务端退出后 socket 文件消失。

第 8 项是最容易写错的地方：客户端断开会触发 socket 的 `error`/`close`，如果事件分发
没有做隔离，一次断开会连带把运行搞掉。

## 12. 验收标准

- [ ] `--serve` + `--connect` 能在两个终端里完成一次完整问答。
- [ ] 第二个客户端能观察同一会话的事件流。
- [ ] 运行中的第二个 prompt 收到 `busy`，第一个运行不受影响。
- [ ] 客户端断开不影响正在跑的运行。
- [ ] `interrupt` 能停掉运行。
- [ ] 版本不匹配给出可读错误。
- [ ] 陈旧 socket 能被接管，活的 socket 拒绝抢占。
- [ ] 目录 `0o700`、socket `0o600`，退出后文件被清理。
- [ ] 服务端横幅打印本次授予的能力。
- [ ] `npm run check`、`npm test`、`npm run build` 全部通过。
- [ ] README（中英）新增远程会话章节与安全说明。
- [ ] 版本提升到 `0.12.0`。

## 13. 不在本阶段

TCP 与远程主机监听、认证与加密、一个服务端多个会话的路由、断线重连与事件重放、
二进制附件、RPC 式的请求/响应（本阶段只有单向广播 + 三条客户端消息）、Windows
命名管道。

下一阶段就只剩 **TUI** 了：扩展 API 里被砍掉的那一半（覆盖层、键位、渲染器）和这一阶段
的远程客户端都在等它。
